# Baseline 정의와 CLI 평가

평가는 **`evaluations/`의 스크립트가 서비스 소스 함수를 직접 호출하고, 터미널 출력과 결과 파일을 보고서에 사용하는 방식**으로 진행한다. 서비스에 평가 화면·메뉴·API 경로·실험 테이블을 추가하지 않는다. 앱은 평가 패키지를 불러오지 않는다.

## 비교 대상

- `baseline-v1` 공지: 저장 공지 서식의 날짜·메뉴·품절 문구를 직접 수정하는 작업 방식.
- `service-v1` 공지: 저장 메뉴와 오늘 선택·품절 상태에서 새 공지를 구성하는 후보 함수.
- `baseline-v1` 홍보 문구: 사진·확인된 사실·스타일 요청을 직접 전달하는 같은 GPT API의 기본 제작 방식.
- `service-v1` 홍보 문구: 저장 상품 정보와 확정 스타일을 전달하는 같은 GPT API의 서비스 방식.

현재 앱 전체를 Baseline으로 삼지 않는다. 두 방식은 모델·입력 사진·사실·출력 스키마를 맞춘다. 정보 재사용과 지시문 차이는 평가 대상이다. 이 실험으로 특정 기능 하나의 효과나 모델 가속을 입증하지 않는다.

자동 스크립트는 사람이 서식을 수정하거나 정보를 입력하는 시간을 측정하지 못한다. 공지 구성·스타일 빈칸 병합 후보는 평가 패키지 안에서 시험하며 서비스 UI에 연결하지 않는다. 사람의 작업 시간·수정 횟수는 실제 사람이 수행한 별도 관찰 기록이 있을 때만 보고한다. 미측정을 0초로 채우지 않는다.

## 실행

저장소 루트에서 실행한다. 자동 검사는 웹 서버와 API 키가 필요 없다.

```bash
.venv/bin/python -m evaluations run
.venv/bin/python -m evaluations list
.venv/bin/python -m evaluations report
```

`run`은 터미널에 실행 ID·통과·실패·미평가 수와 파일 위치를 JSON으로 출력한다. `report`는 모든 실행을 CSV·Markdown으로 집계한다. 저장 위치를 바꾸려면 `--results-dir /원하는/경로`를 붙인다. 별도 평가 DB를 만들지 않고 JSON 파일을 저장한다.

실제 GPT 비교는 아래 명령으로만 별도 실행한다. **실행할 때마다 유료 요청 8건**이 추가되며 각각 입력 토큰 사전 조회도 발생한다. 기존 프로젝트의 비용 원장·통합 예산·계정 호출 한도를 그대로 사용한다. 원장이 없거나 설정이 부족하면 중단하며 한도를 자동으로 늘리지 않는다.

```bash
.venv/bin/python -m evaluations live \
  --env-file /path/to/content-marketing-ai/.env
```

이번 구조 정리에서는 실제 API를 재호출하지 않는다. 기존 유료 파일럿 8건을 보존해 집계한다.

## GSM과 판정 기준

### G1. 정확한 콘텐츠 제작

과제 자료는 라인업 스토리·라인업 피드·품절 스토리·상품 소개·행사 안내·가게 소개 6종이다. 자동 공지 검사는 선택 메뉴·제외 메뉴·날짜·품절·출력 규격을 확인한다. GPT 문구는 원본 응답과 제한된 숫자·미확인 표현 검사 결과를 함께 남긴다. 이 검사를 통과했다고 사실 정확도 100%로 간주하지 않는다.

- `execution_ms`: 평가 함수 실행 시간. 실제 API 경로에서는 사전 조회·생성·검증까지의 실행 시간을 포함한다.
- `generation_api_ms`: 실제 생성 요청부터 응답 수신까지.
- `preflight_api_ms`: 입력 토큰 사전 조회 시간.
- `human_task_ms`: 실제 사람의 전체 작업 시간. 자동 실행에서는 `null`이다.

과거 JSON의 `server_ms`는 당시 계측 필드명으로 보존하고 현재 집계에서는 `execution_ms`로 읽는다. 브라우저 표시·실제 게시·사람의 입력 및 검수 시간은 CLI의 API 응답 시간으로 대체하지 않는다. 스토리 5초·피드 15초는 사용자 요구의 초기 목표이며, 문구만의 응답으로 전체 피드 목표 달성을 주장하지 않는다. 수정 2회 이내는 품질 목표이며 사용 횟수 제한이 아니다.

### G2. 근거 있는 스타일 자동 입력

자동 검사 3개는 빈칸만 채우기·기존 값 보존·근거 없는 빈칸 유지의 **후보 병합 규칙**을 확인한다. AI 추출 정확도와 구분한다.

실제 추출 결과는 평가자가 6개 속성을 자료와 대조해 판정한다. 관찰 가능한 항목은 올바른 채움·누락·오입력, 관찰 불가능한 항목은 적절한 빈칸·근거 없는 채움으로 기록한다. 올바른 채움 수/관찰 가능한 항목 수를 계산하고 근거 없는 채움도 별도로 센다. 분모가 없으면 정확도는 비워 둔다.

### G3. 근거에 맞는 인사이트와 제안

`app.analytics.analyze()`에 합성 자료를 직접 넣는다. 일반 홍보 피드만 같은 목적·관측 시점으로 비교하고 라인업·스토리·유료 홍보·미확인 조건은 제외한다. 결측·도달 0·음수·불리언을 유효한 비율로 취급하지 않는다.

- MFT 12개: 비율 계산·분모 0·누락·형식·목적·시간·광고 여부·잘못된 값.
- INV 3개: 입력 순서·제외 대상 추가·분자와 분모의 비례 확대.
- DIR 2개: 저장만 증가할 때 비율 증가, 필요한 지표가 누락되면 비교 철회.

17개는 기능별 개발 계약 검사이며 독립 평가 표본이나 충분한 통계 표본을 뜻하지 않는다. 24±2시간은 이 자료의 검사 조건이다. 규칙 기반 브리핑 검사와 실제 GPT 자연어 품질 검수를 분리한다.

## 사람이 결과를 검수할 때

결과 파일과 입력을 대조해 JSON에 판단을 작성하고 CLI로 반영한다. 별도 화면을 만들지 않는다.

```bash
.venv/bin/python -m evaluations review-template --run-id 실행ID > review.json
# review.json의 평가자·항목 판정·근거를 직접 작성한 뒤 실행
.venv/bin/python -m evaluations review --run-id 실행ID --review-file review.json
.venv/bin/python -m evaluations report
```

평가자 관계는 개발자 자체 평가·동료·강사로 구분한다. 응답과 입력은 덮어쓰지 않고 판정 이력을 추가한다. 사람이 작성하지 않은 판단을 human evaluation으로 기록하지 않는다. 실제 사용자 반복 사용·홍보 효과·매출은 이 내부 평가로 입증하지 않는다.

## 버전과 결과 파일

현재 실행 프로토콜은 `evaluation-1.1.0-cli`, 고정 자료는 `fixtures/tasks-v1.json`과 `fixtures/checklist-v1.json`이다. 각 실행에 방식 버전·전체 소스 해시·Git 커밋·모델·설정·자료 해시·입력·원본 응답·실패·토큰·비용·시간을 보존한다. 키·토큰·`.env`·운영 DB는 소스 ZIP에 포함하지 않는다.

`evaluations/results/`에는 다음 파일을 남긴다.

- `runs/`: 실행별 원본 JSON. 평가용 DB 대신 파일로 저장한다.
- `exports/<실행ID>/`: 원본 JSON·검사 CSV·시도별 CSV·요약 Markdown.
- `snapshots/`: 실행 당시 소스·평가 코드·자료·글꼴 및 라이선스 ZIP.
- `report/`: 호출별 비용·토큰·시간 CSV, 자동 검사 CSV, 사람 판정 CSV, Markdown 집계.
- `legacy/`: 제거한 평가 화면에서 생성했던 임시 상태와 이전 저장 파일. 현재 실행에서는 읽지 않는다.

`results/`는 Git에서 제외한다. 공개 보고서에 사용할 수치만 `evaluations/reports/`에 복사해 관리하며, 원본 입력·응답·사진·실행 DB·소스 ZIP과 설정 파일은 포함하지 않는다. 저장소에서 확인 가능한 첫 파일럿 수치는 [공개 결과](../evaluations/reports/pilot-2026-10-26/README.md)에 있다.

이전 11개 실행과 유료 응답 8건은 내용과 코드 해시를 유지해 옮겼다. 이전 소스 ZIP에 당시 화면 코드가 남아 있는 것은 실행 증거 보존을 위한 것이다. 현재 앱에 평가 기능이 연결되어 있다는 의미가 아니다. 재실행 결과로 이전 결과를 덮어쓰지 않는다. 비용은 설정 단가로 계산한 앱 원장 기록액이며 공급자 청구서와 구분한다.

## 설계 출처

[HEART/GSM 연구](https://research.google/pubs/measuring-the-user-experience-on-a-large-scale-user-centered-metrics-for-web-applications/)는 목표·신호·지표 연결에, [CheckList 원 논문](https://aclanthology.org/2020.acl-main.442/)과 [저자 구현](https://github.com/marcotcr/checklist)은 MFT·INV·DIR 행동 검사에 참고했다. 두 자료가 우리 시간 목표나 검사·호출 개수와 실사용 효과를 검증한 것은 아니다.
